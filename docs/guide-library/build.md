# Build

## Build A Wave Someone Can Use

A Guide turns the agreed brief into a custom experience. Start with the smallest phone your audience is likely to use. The story should be readable, the next move clear, and the action possible without needing to understand how the platform works.

Use the shared Wave identity and Journey so the work keeps its home over time. Customize the layout, tools, media, and connections around the builder's needs. Code and generated designs still require human review before they reach visitors.

## Make The First Working Version

1. Arrange the public experience around **the story, the next move, and the outcome**. Let visitors understand each before adding more detail.
2. Build the participation path end to end: open the form, understand the request, submit once, receive confirmation, and learn what happens next.
3. Separate public content from workspace records. A draft, email address, budget note, or private document must not become public simply because a view needs data.
4. Add appropriate feedback for loading, success, failure, empty content, and interrupted connections. Preserve a person's work when a request fails.
5. Test keyboard access, labels, visible focus, touch targets, contrast, zoom, and reduced motion. Animation should support an action and remain optional.
6. Review the complete experience with the builder and at least one person who did not build it. Publish the approved version and keep the source and configuration documented.

## An Annotated Example

**Maker Wave — The Community Build Kit.** This is an illustrative teaching case.

The first version shows the build brief, parts needed, open roles, and a way to offer a skill. The parts file has a version and permitted-use statement. A working demonstration and handover notes are published after the builder reviews them.

**Why this matters:** the graphic helps people understand the kit, while the participation path lets them help make it. A polished mockup alone does not show that the kit works.

## Connect Only What You Can Verify

A social link can take someone to a Wave today. An embedded experience or automated publishing connection depends on that platform's supported access and permissions. Describe the connection that exists, test it, and record who owns its account. Store credentials securely outside public content and exports.

Keep dependencies, service costs, domains, and maintenance responsibilities visible to the builder. Agree on the ownership and license of custom code, reusable components, media, and third-party materials rather than assuming they all transfer together.

## Guide Tips

- Use real labels and a clear action before refining motion.
- Give images useful alternative text and videos appropriate captions or equivalent explanation.
- Test a failed submission as carefully as a successful one.
- Keep custom code reviewable. Maintain a recovery path before replacing a public experience.

## Your Deliverable

A builder-approved Wave with a tested participation path, documented source, accessible mobile experience, and named maintenance owner.

## Before You Move On

- [ ] A new visitor can explain the story and next move.
- [ ] A real test completes the participation path and confirms receipt.
- [ ] Private content stays private across pages and direct requests.
- [ ] Phone, keyboard, zoom, and reduced-motion checks pass.
- [ ] Source, account ownership, dependencies, and recovery instructions are documented.
